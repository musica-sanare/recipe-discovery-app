# データソース — Recipe Discovery

Recipe Discovery が使うデータと、その利用条件、出典表示、リポジトリでの抽出と管理の方法をまとめる。ライセンスを確かめる人や、成分データを更新する人に向けている。使っているデータソースは文部科学省の食品成分表だけだ（§1）。§2 には、検討したが使わなかったデータソースを挙げる。

状態：**運用中**。以下の利用条件と事実は、2026-10-18 に引用元のページで確認した。利用条件は変わりうるので、リリースの前に確認し直す。

### 利用条件

- *検証済み*（https://www.mext.go.jp/a_menu/syokuhinseibun/index.htm）：食品成分のデータは自由に使える。論文、書籍、アプリケーションなどで二次利用するときは、出典を「日本食品標準成分表（八訂）増補2023年から引用（又は出典）」と書くよう文部科学省が求めている。
- *検証済み*（https://fooddb.mext.go.jp/）：オンラインのデータベースは試験的なサービスで、その利用で生じた損害について文部科学省は責任を負わない。このプロジェクトはオンラインのデータベースではなく、公開されているワークブックを使う。
- オーナーの立場（2026-10-18）：データを計算の基礎として使い、アプリの中で出典を示す。別に問い合わせる予定はない。アプリでは、値がアプリ独自の計算で、文部科学省が承認したものではないことも示す。
- 利用についての問い合わせ先（文部科学省のページより）：kagseis@mext.go.jp。
- 出典表示の文言と表示場所は [CONTENT_POLICY.md](CONTENT_POLICY.md) §5 にある。

### 抽出したデータのライセンス

- リポジトリは [MIT ライセンス](../../LICENSE) だ（ADR-031）。ただし `data/composition/` は除く。
- `data/composition/` の値は文部科学省の成分表に由来する。`foods.json` はワークブックから抽出したもの、`cooking.json` は説明の PDF の表 12〜14 を書き写したもので、`manifest.json` が出典を記録している。
- このプロジェクトは、文部科学省の値について権利を主張しない。これらのファイルは、上の文部科学省の利用条件に従って使い、共有している。再利用する人も、出典の記載「日本食品標準成分表（八訂）増補2023年から引用（又は出典）」を含め、その条件に従う。

### 取り扱いのルール

> [!WARNING]
> 元のワークブックはコミットしない。`data/raw/`（Git の管理外）かリポジトリの外に置く。

- スクリプトで、食品辞書が参照する食品番号と、アプリが使う列だけを抽出する。記号の印（`-`、`Tr`、`(0)`、`(Tr)`、`( )`）は残す。
- 抽出した成分の一部とマニフェストは Git で管理する。そのため、元のファイルがなくてもビルドを再現できる。マニフェストには、取得元の URL、ワークブックの更新日、SHA-256、抽出スクリプトの版、抽出日を記録する。
- データソースの更新：
  1. 新しいファイルをダウンロードする。
  2. マニフェストを更新する。
  3. 抽出をやり直す。
  4. 栄養のスナップショットの差分を確認する。
  5. 変更を [DECISIONS.md](../working/DECISIONS.md)（英語のみ）に記録する。

### 既知の制限

- 八訂には公式の英語の食品名がない。PDF（今後の課題の章）で *検証済み*：英語版や翻訳の機能は「検討中」とされている。2015 年版は日本語と英語で公開された。その英語名と食品番号を参考にできるかは 要確認。
- 重量変化率（表 12）と、揚げ物・いため物の脂質のデータ（表 13〜14）は PDF にあり、ワークブックにはない。
- 目安量の表がない。

### 抽出（フェーズ 0 Stage 0.2 で実装）

- ワークブックは、`data/composition/manifest.json` の `rawFile` が示すパスに置く。今は `data/raw/mext/20260327-mxt_kagsei-mext-000029402_02.xlsx`（Git の管理外）だ。
- `npm run data:extract` は SHA-256 をマニフェストと照らし合わせ、マニフェストにあるシート（`表全体`）を読む。そして `requestedCodes` に挙げた食品番号で `data/composition/foods.json` を書き出す。出力は決定論的だ（食品番号順、タイムスタンプなし）。
- `node tools/extract-composition.ts --search <regex>` は、一致する食品番号と名前を一覧にする。番号を選ぶときに使う。
- 列は位置ではなく、成分識別子の行と日本語の見出しで見つける。
  - 抽出する識別子：`REFUSE`、`ENERC_KCAL`、`PROT-`、`PROTCAA`、`FAT-`、`FATNLEA`、`CHOAVLDF-`、`CHOCDF-`、`FIB-`、`NACL_EQ`（`shared/composition.ts`）。
  - 各値は記号の区分（`measured`、`zero`、`trace`、`estimated`、`estimated_zero`、`estimated_trace`、`unmeasured`）を残す。認識できないセルの内容があると、抽出は止まる。
- 食品名は公開されているとおり日本語だけを残す。すべてのロケールでの表示名は食品辞書が持つ（Stage 0.4）。
- テストで、管理している成分の一部を、ワークブックなしでスキーマとマニフェストに照らして検証する。

### 調理の表（フェーズ 0 Stage 0.3 で実装）

- 表 12（重量変化率）、表 13（揚げ物）、表 14（油いため・ソテー）は説明の PDF にしかない。
- PDF のテキスト層では表の列が入り乱れる。そこで、必要な行は描画したページの画像から `data/composition/cooking.json` に**手で書き写して**いる。各項目にはページ番号を、ファイルには PDF の SHA-256（`d1196cc8…f116`、ファイル `data/raw/mext/20260327-mxt_kagsei-mext-000029402_0001.pdf`、Git の管理外）を記録している。
- `rawCode`（各調理後の食品と組になる生の食品）は、このプロジェクトが割り当てたものだ。数値はすべて文部科学省のもので、印刷どおりに書き写している。元データには既知の不整合が 1 つある：食品 11290 は表 12 で 82 %、表 13 で 81 g だ。
- 検証：
  1. `npm run data:verify-cooking`（macOS のみ。`tools/macos/pdf-page-text.swift` 経由で PDFKit を使う）は、書き写した数値と食品番号がすべて、PDF のテキスト層の該当ページにあることを確かめる。弱点：テキスト層は列の順に並ぶので、同じページのほかの場所にも出てくる数値は通ってしまう。
  2. `test/node/cooking-data.test.ts` のテストは、PDF なしで毎回のチェックで動く。確かめるのは、衣のない食品のたんぱく質の残存率（60〜115 %）、成分値から計算し直した表 13〜14 の脂質の変化（1 g 以内）、表 12 と表 13〜14 の調理後の重さの整合、衣を含む基準の変化率が主材料の変化率より低いことだ。2026-10-18 に、わざと入れた書き写しの誤り（61 → 16、4.6 → 6.4）をこれらのテストが見つけた。
- 食品の追加：
  1. ページを描画し、その行をページ番号とともに書き写す。
  2. 生と調理後の食品番号をマニフェストに加える。
  3. `npm run data:extract`、`npm run data:verify-cooking`、テストを実行する。

## 2. 検討したが MVP では使わないもの

| データソース | 利用条件（2026-10-18 確認） | 使わない理由 |
|---|---|---|
| USDA FoodData Central | CC0 1.0 パブリックドメイン。出典表示を要請。API には api.data.gov のキーが必要。既定の上限は IP あたり 1 時間に 1,000 リクエスト | 日本の成分表との公式の対応がない（二次的なデータソース）。英語名にも結局対応付けが要る。後で英語の名前付けの参考になるかもしれない |
| Open Food Facts | データベースは ODbL（出典表示と継承）、内容は DbCL、画像は CC BY-SA | 生の材料ではなく包装された製品が対象。ほかのデータと組み合わせると継承の義務が生じる |
